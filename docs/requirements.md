# tably — 요구사항 시나리오 v0.2

> 예약금 기반 노쇼 방지 레스토랑 예약 서비스 (실서비스 운영 가정 기준)
> 최종 수정: 2026-07-21 / 작성자: 김우영

---

## 1. 서비스 정의

### 어떤 문제를 푸는가
- 외식업 노쇼로 인한 손실은 업계의 고질적 문제다. 특히 예약제 파인다이닝·오마카세는 노쇼 1건 = 그 타임 매출 전체 손실이다.
- 식당은 노쇼를 막고 싶고, 손님은 인기 식당 예약을 공정하게 잡고 싶다.
- **tably는 예약금을 걸어 노쇼를 줄이고, 예약 오픈 경쟁을 공정하게 처리하는 예약 플랫폼이다.**

### 비즈니스 모델
- 노쇼 위약금의 일부를 플랫폼 수수료로 수취 (예: 위약금의 10%)
- 식당에게는 월 단위로 위약금 수익을 정산 지급

### 서비스 범위 (v1)
- 예약제 식당의 **예약 + 예약금 + 웨이팅 + 정산**
- 검색/리뷰/지도 등 디스커버리 기능은 범위 외 (식당 목록은 존재한다고 가정)

## 3. 시나리오 — 서비스에서 실제로 벌어지는 일들

### S1. 식당 입점과 예약 정책 설정 (사장)

박성호 사장은 입점 후 예약 정책을 설정한다.

- 운영 타임: 매일 18:00 / 20:30, 타임당 테이블 4개 (2인 기준)
- 예약금: 1인당 20,000원
- 예약 오픈 방식: **매월 1일 오전 10:00에 다음 달 전체 오픈**
- 취소·환불 정책: 7일 전 100% / 3일 전 50% / 1일 전~당일 0%
- 휴무일 지정: 매주 월요일 + 임시 휴무

**여기서 나오는 요구사항:**
- 식당별로 타임/테이블/예약금/환불정책이 다르다 → 정책은 하드코딩이 아니라 데이터로 관리
- 예약 슬롯은 정책 기반으로 **미리 생성**된다 (매월 오픈 시점에 다음 달 슬롯 일괄 생성)
- 휴무일 지정 시 해당일 슬롯은 생성되지 않거나 닫힌다

### S2. 예약 오픈런 (손님)

7월 1일 09:55. 김지현은 알림을 받고 앱을 켠 채 대기 중이다. 「스시 준」 8월 예약 오픈을 기다리는 사람은 그녀만이 아니다 — 약 5,000명이 240개 슬롯(30일 × 2타임 × 4테이블)을 노린다.

10:00:00. 김지현은 8월 15일 20:30 타임을 터치한다.

- **성공하면:** "예약금 결제를 10분 안에 완료해주세요" — 슬롯이 그녀 몫으로 10분간 선점된다
- **실패하면:** "방금 마감되었습니다" — 즉시, 명확하게. 로딩만 돌다가 에러가 나면 유저는 이탈한다

10:00:07. 240개 슬롯이 모두 선점됐다. 4,700명은 실패 응답을 받았다.

**여기서 나오는 요구사항:**
- 같은 슬롯에 2명이 예약되는 사고는 서비스 신뢰의 근간 — **중복 예약 0건은 타협 불가**
- 실패 응답도 빨라야 한다 (실패한 다수가 서버를 붙잡고 있으면 전체가 느려진다)
- 10분 내 미결제 슬롯은 자동으로 풀려서 대기하던 다른 손님이 잡을 수 있어야 한다
- 오픈 직후 트래픽은 평시의 수백 배 → 부하 테스트로 검증

### S3. 예약금 결제 (손님)

김지현은 2인 예약이므로 예약금 40,000원을 결제한다.

- 지하철에서 결제하다 네트워크가 끊겨 **결제 버튼을 두 번 눌렀다** → 청구는 한 번만 되어야 한다
- 결제 요청 후 PG 응답이 오지 않았다(타임아웃). 앱은 실패로 보였는데 **카드사 문자로는 승인 알림이 왔다** → 이 상태를 방치하면 "돈은 나갔는데 예약은 없는" 최악의 CS가 터진다. 시스템은 승인 여부를 PG에 재확인해서 정합성을 맞춰야 한다
- 결제 완료 → 예약 확정. 확정 내역에는 일시/인원/예약금/환불 정책이 명시된다 (분쟁 시 근거)

### S4. 취소와 환불 분쟁 (손님 → CS)

8월 14일 밤, 김지현의 아이가 갑자기 아프다. 방문 하루 전 취소 — 정책상 환불 0%.

- 앱은 취소 전에 **"지금 취소하면 환불액 0원"임을 명확히 고지**하고 확인을 받는다 (고지 없으면 CS 폭탄)
- 김지현은 그래도 억울해서 CS에 문의한다 → 운영자는 예약 시점에 고지된 정책과 동의 기록을 근거로 답변한다
- 반대로 7일 전 취소였다면: 환불 40,000원이 즉시 진행된다. **환불 처리 중 PG 오류가 나면** 실패 상태로 기록하고 자동 재시도한다 — "취소했는데 돈이 안 들어와요"는 실제 서비스에서 가장 흔한 결제 CS다
- 취소된 슬롯은 다시 예약 가능해진다

### S5. 방문 당일, 그리고 노쇼 오처리 분쟁 (사장 ↔ 손님)

8월 15일 20:30. 이 타임 예약자는 4팀.

- 3팀은 정상 방문 → 박사장이 태블릿에서 "방문 완료" 처리 → 예약금 자동 환불
- 1팀은 나타나지 않음 → 21:00(예약 +30분)에 시스템이 자동으로 노쇼 처리 → 예약금 몰수

**그런데 실제 서비스에서 진짜 터지는 문제는 이거다:**
바쁜 저녁 영업 중에 박사장이 **방문 완료 처리를 깜빡했다.** 멀쩡히 와서 식사한 손님이 노쇼 처리되고 예약금 40,000원을 뺏겼다. 다음 날 별점 테러와 CS 항의가 들어온다.

**여기서 나오는 요구사항:**
- 노쇼 자동 처리 전에 유예를 둔다 (예: 당일 자정까지는 사장이 방문 처리 정정 가능)
- 노쇼 확정 후에도 **이의신청 → 운영자 검토 → 노쇼 철회 + 환불** 흐름이 필요하다
- 즉, 노쇼는 "몰수 끝"이 아니라 **번복 가능한 상태**로 설계해야 한다. 이미 몰수(정산 반영)된 뒤 철회되면 정산에서 차감해야 한다

### S6. 당일 웨이팅 (손님 ↔ 사장)

예약이 꽉 찬 날에도 취소·노쇼로 자리가 난다. 「스시 준」은 당일 원격 웨이팅을 받는다.

- 김지현은 오후 5시에 원격 줄서기 등록 → 대기 12번
- 앱에서 "내 앞에 7팀" 실시간 확인 (폴링)
- 자리가 나자 박사장이 "다음 팀 호출" → 김지현에게 차례가 온다 → **10분 내 도착 확인이 없으면 자동으로 순번이 넘어간다**
- 호출을 놓친 김지현은 대기가 만료됐다. "한 번 더 기회" 정책(1회 순연 후 만료)은 v1 범위에서 제외하되 설계 시 고려

**여기서 나오는 요구사항:**
- 동시에 등록해도 대기 번호 중복·누락 없음
- 순번 조회는 매우 잦다(모두가 계속 새로고침) → 조회는 가볍게
- 호출 만료의 시간 기반 자동 처리

### S7. 월말 정산 (사장 ↔ 플랫폼)

9월 1일 새벽, 8월분 정산 배치가 돈다.

- 「스시 준」 8월 노쇼 위약금: 6건, 240,000원
- 플랫폼 수수료 10% 차감 → 216,000원 지급 예정
- 그런데 8월 노쇼 중 1건이 9월 2일에 이의신청 인용으로 철회됐다 → **이미 지급된 40,000원은 9월 정산에서 차감(마이너스 이월)**
- 박사장은 정산서에서 "왜 이 금액인지" 건별 내역을 확인할 수 있어야 한다 — 내역 없는 정산은 CS를 부른다

**여기서 나오는 요구사항:**
- 정산 배치는 중간에 죽어도 재실행 시 **중복 지급 없음**
- 정산서 = 합계가 아니라 건별 내역의 집합
- 정산 확정 후 발생한 번복 건은 다음 회차에서 조정

### S8. 식당 임시 휴업 — 대량 취소 (사장 → 운영자)

8월 20일, 박사장이 주방 화재로 열흘 휴업하게 됐다. 해당 기간 확정 예약이 80건이다.

- 운영자(또는 사장)가 기간 휴업을 등록하면 → 해당 기간 예약 80건이 **일괄 취소 + 전액 환불** (귀책이 식당이므로 환불 정책 무시하고 100%)
- 80건 환불 중 3건이 PG 오류로 실패했다 → 실패 건만 기록되어 재처리된다. 나머지 77건이 롤백되어서는 안 된다
- 해당 기간의 미오픈 슬롯은 닫힌다

**여기서 나오는 요구사항:**
- 대량 처리는 "전부 성공 아니면 전부 실패"가 아니라 **건별 성공/실패 추적 + 실패 건 재처리** 구조
- 귀책 사유에 따라 환불 정책이 달라진다 (손님 취소 vs 식당 취소)

## 4. 예약 상태 머신 (v0.2 — S5 반영)

```
슬롯 선점
   ▼
PENDING_PAYMENT ──(10분 미결제)──▶ EXPIRED
   ▼ 결제 완료
CONFIRMED ──(손님 취소)──▶ CANCELED_BY_USER (시점별 환불)
   │       ──(식당 취소)──▶ CANCELED_BY_SHOP (전액 환불)
   ├──(방문 처리)──▶ VISITED (예약금 환불)
   └──(+30분, 배치)──▶ NO_SHOW (예약금 몰수)
                          │
                          ├─(당일 내 사장 정정)──▶ VISITED
                          └─(이의신청 인용)──▶ NO_SHOW_REVOKED (환불 + 정산 차감)
```

결제 상태는 별도 관리: `READY → APPROVED → CANCELED / PARTIAL_CANCELED / FAILED / UNKNOWN`

> **설계 결정 (2026-07-21):** 예약(reservation)과 결제(payment)는 테이블 분리.
> 결제 시도 1번 = payment 1행 — 사건은 덮어쓰지 않고 쌓는다.
> 근거: 실패/UNKNOWN 이력 보존, PG 재확인 대상 식별, CS 대응.

## 5. 기능 요구사항 (FR) — 시나리오에서 도출

### 회원·인증 — P0
- FR-00 회원가입 + JWT 로그인 (Spring Security), 손님/사장 권한(Role) 분리
  - 범위 제한: 소셜 로그인, 이메일 인증, 비밀번호 찾기는 제외

### 식당·정책 (S1)
- FR-01 예약 정책 등록/수정 (타임, 테이블 수, 예약금, 환불율, 휴무)
- FR-02 오픈 시점 슬롯 일괄 생성

### 예약 (S2) — P0
- FR-03 슬롯 조회 / FR-04 슬롯 선점 (동시성, 중복 0건) / FR-05 선점 10분 만료

### 결제 (S3) — P0
- FR-06 예약금 결제 (멱등성) / FR-07 UNKNOWN 상태 재확인 처리

### 취소·환불 (S4, S8) — P0
- FR-08 시점별·귀책별 환불 계산 / FR-09 환불 실패 기록·재처리
- FR-10 식당 휴업 일괄 취소 (건별 추적)

### 방문·노쇼 (S5) — P1
- FR-11 방문 완료 처리 + 당일 정정 / FR-12 노쇼 자동 전환 배치
- FR-13 노쇼 이의신청·철회 (정산 조정 연동)

### 웨이팅 (S6) — P1
- FR-14 등록·순번 발급 / FR-15 순번 조회 / FR-16 호출·10분 만료

### 알림 — P1
- FR-20 도메인 이벤트 발행(예약 확정/취소/노쇼/웨이팅 호출) → 비동기 알림 처리
- FR-21 알림 기록 저장 + 발송 실패 재시도 (실제 채널은 로그/콘솔로 대체)

### 정산 (S7) — P2
- FR-17 월 정산 배치 (재실행 안전) / FR-18 건별 정산 내역 / FR-19 마이너스 이월

> **기준선(10~12주): P0 완성 = 성립, P1 + Redis 전환까지 = 목표, 프론트 = 마지막 1~2주, P2 정산 = 여유 시**

## 7. 스코프 로드맵 — 만드는 것 / 나중에 만드는 것 / 안 만드는 것

### ✅ 처음부터 만든다 (1막)
- 회원가입 + JWT 로그인 + 손님/사장 권한 분리 (FR-00)
- 예약 동시성은 **DB 락으로 먼저 구현** (비관적/낙관적 락 비교 실험)
- 알림은 이벤트 발행 + 비동기 처리 + 실패 재시도 구조로 구현하되, 발송 채널은 로그/콘솔

### 🔜 검증 후 만든다 (2막 — 이 순서가 면접 서사의 핵심)
- **Redis**: DB 락 구현 → k6 부하 테스트로 한계 수치 확보 → Redis 분산락(슬롯 선점)·Sorted Set(웨이팅 대기열)으로 전환 → 전환 전후 성능 비교를 README에 기록
  - "썼다"가 아니라 "필요를 측정으로 증명하고 도입했다"를 만들기 위한 순서
- **프론트 화면**: 백엔드 P1 완성 후 마지막 1~2주에 React로 핵심 2화면만
  - ① 오픈런 예약 화면 (슬롯 선택 → 선점 → 결제) ② 웨이팅 순번 화면 (실시간 순번 폴링)
  - 사장/관리자 기능은 Swagger로 시연
